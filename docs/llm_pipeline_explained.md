## 0. 先看结论（5 分钟版）

这个项目做的事情可以一句话概括：

> **用一份很小的中文语料，从零训练一个小语言模型，把它压缩成更小的文件，再用 llama.cpp 跑起来，最后测量"压缩后小了多少、质量掉了多少、速度快了多少"。**

| 问题 | 结论 | 证据 |
|---|---|---|
| 模型能训出来吗 | 能。4 层、4,162,816 个参数，CPU 上 150 轮约 60 秒 | `out/reports/train.md` |
| 能压小吗 | 能。F16 8.45 MB → Q4_K_M 2.71 MB，约为原来的 32% | `out/reports/quantize.md` |
| 量化后精度如何 | **不能下结论**。PPL 2046 → 2043，差异在噪声内 | `out/benchmark.md` |
| 量化后更快吗 | **不保证**。CPU 上 Q4 解码约 2000 tok/s，F16 约 2174 tok/s | `out/benchmark.json` |
| 投机解码有用吗 | 有加速，1.17×；但接收率没有测到 | `out/spec_decode.md` |
| LoRA SFT 有用吗 | 链路跑通；17 条样本、loss 7.39，没有质量对比 | `out/reports/sft.md` |
| GQA 有收益吗 | **没有做消融**，无法量化收益 | `config.yaml` |
| imatrix 有效吗 | **记录里没有真正使用**，无法下结论 | `out/quantize_sweep.md` |

先记住一句话：**这个项目的最大价值不是"训出了一个聪明模型"，而是把"训练 → 压缩 → 部署 → 测量"整条工程链路走通了，并且留下了可复现的数字。**

## 1. 大模型到底在干什么

### 1.1 一句话：预测下一个词

语言模型做的事情非常朴素：

```
输入：人工智能是计算机科学的
输出：一个分支
```

模型不是"理解"了这句话，而是学会了：**在给定前文的情况下，下一个 token 最可能是什么。**

训练时，它不停地做"完形填空"：

```
人工智能是计算机科学的 ___
正确答案：一个
```

猜错了就调整内部参数，猜对了就保持。重复几十万、几百万次，模型就学会了语言的统计规律。

### 1.2 为什么叫"大"模型

模型内部有很多数字，叫**参数**（weights）。参数越多，模型能记住的规律越复杂，但文件越大、计算越慢。

本项目的 draft 模型只有 **4,162,816 个参数**（约 4.16M），而 GPT-3 是 175B（1750 亿），差了四万多倍。所以它只能算一个"教学用的小模型"。

## 2. 第一步：把文字变成数字（Tokenizer）

### 2.1 为什么不能直接处理文字

计算机擅长算数，不擅长直接处理"人"这个字。所以要先把文字切成小块，再把每个小块映射成一个整数。

这些小块叫 **token**。

```
"人工智能" → ["人工", "智能"] → [1234, 567]
```

### 2.2 什么是 BPE

BPE（Byte Pair Encoding）的思路像"拼积木"：

1. 一开始，每个字节都是一块小积木；
2. 统计哪两块经常挨在一起；
3. 把最常一起出现的两块粘成一块更大的积木；
4. 重复很多次，直到词表达到目标大小。

所以常见的词会变成一整块，罕见的词会被拆成几块。这样既不会"完全不认识"，又能让常用词只占一个 token。

### 2.3 本项目的 tokenizer 怎么训练

代码在 [pipeline/train.py](../pipeline/train.py:40) 的 `train_tokenizer()`：

1. 用 `models.BPE()` 建一个空的分词器；
2. 用 GPT-2 的正则规则做预切分（按英文缩写、字母、数字、符号、空白切开）；
3. 用 ByteLevel 把每个字符映射成字节，保证中文也不会变成"未知词"；
4. 用 `BpeTrainer` 在 `data/corpus.txt` 上训练，目标词表 2048；
5. 加入四个特殊 token：`<|unk|>`、`<|bos|>`、`<|eos|>`、`<|pad|>`；
6. 保存到 `models/tokenizer/`。

### 2.4 实际结果

| 项目 | 数值 |
|---|---:|
| 语料大小 | 2,667 个字符 / 47 个非空行 |
| 目标词表 | 2048 |
| 实际词表 | **1982** |
| bos / eos / pad id | 1 / 2 / 3 |

为什么实际只有 1982？因为语料太小，能合并的字节对很快就被用完了，达不到 2048。这不是 bug，而是"目标值"和"实际能训到多少"的区别。

### 2.5 为什么 draft 和 target 必须共用词表

投机解码时，draft 先猜出一串 token id，target 要在**同样的 id** 上打分。如果两个模型的词表不一样，同一个 id 在两边代表不同的字，猜得再多也没意义。

所以 target 训练时要加 `--reuse-tokenizer`，直接复用 draft 的词表。

## 3. 第二步：把 token 变成训练样本

### 3.1 一句话：把长文章切成固定长度的小段

模型一次只能看固定长度的内容（这里是 256 个 token）。所以要把整篇文章切成很多段，每段 256 个 token。

代码在 [train.py](../pipeline/train.py:82) 的 `build_dataset()`：

```python
ids = tokenizer.encode(text)
step = block_size // 2          # 128，半重叠
chunks = [ids[i:i + block_size + 1] for i in range(0, len(ids) - 1, step)]
```

为什么要多取 1 个 token？因为语言模型的输入和答案要错开一位：

```
输入: [人, 工, 智, 能]
答案: [工, 智, 能, 是]
```

模型看到前 3 个，要猜第 4 个；看到前 4 个，要猜第 5 个。这样一段 257 个 token 就能同时提供 256 个训练信号。

### 3.2 为什么要半重叠

如果每段完全不重叠，段与段之间的上下文会丢失。半重叠（步长 128）能让相邻样本共享一部分内容，小语料也能切出更多样本。

## 4. 第三步：模型内部长什么样（Transformer）

### 4.1 先看整体

本项目的模型是一个 **LLaMA 架构**的 Transformer，draft 版本配置是：

| 配置 | 数值 |
|---|---:|
| 层数 | 4 |
| hidden 维度 | 256 |
| 注意力头数 | 4 |
| KV 头数 | 2（GQA） |
| FFN 中间维度 | 768 |
| 最大上下文 | 512 |
| 词表 | 1982 |

每一层做的事情可以粗略理解成：

```
输入向量
  → 自注意力（看看别的词）
  → 残差连接
  → 前馈网络（自己想一想）
  → 残差连接
  → 输出向量
```

### 4.2 Embedding：给每个 token 一个坐标

每个 token id 会被查表变成一个 256 维的向量。你可以把它想成"这个字在语义空间里的坐标"。

比如"猫"和"狗"的坐标可能比较近，"猫"和"微积分"的坐标比较远。

### 4.3 自注意力：Q、K、V 是什么

这是 Transformer 最核心的部分。用一个图书馆的类比：

- **Query（Q）**：我想找什么？（比如"我在找一只动物"）
- **Key（K）**：每本书的标签是什么？（比如"这是一本关于动物的书"）
- **Value（V）**：书里真正的内容。

计算过程：

1. 每个词生成自己的 Q、K、V；
2. 用当前词的 Q 去和所有词的 K 做点积，得到"相关性分数"；
3. 用 softmax 把分数变成权重（总和为 1）；
4. 用权重对所有 V 加权求和，得到这个位置的新表示。

公式：

```
Attention(Q, K, V) = softmax(QKᵀ / √d) · V
```

`√d` 是为了防止数字太大，softmax 后过于极端。

### 4.4 因果掩码：不能偷看答案

训练时，模型不能看到后面的词，否则就是作弊。所以要用一个"因果掩码"，把当前位置之后的所有分数设成负无穷，softmax 后权重变成 0。

这就是"自回归"：只能根据前面的内容预测下一个。

### 4.5 多头注意力

一个注意力头只能学一种"关注方式"。多个头可以分别关注语法、指代、语义等不同关系。

本项目有 4 个 Q 头，每个头 64 维（4 × 64 = 256）。

### 4.6 GQA：几个 Q 头共用一组 K/V

标准多头注意力（MHA）是每个 Q 头都有自己的 K/V 头。GQA 是"分组共享"：

```
Q0 Q1   Q2 Q3
 |  |     |  |
 K0       K1
```

本项目 4 个 Q 头、2 个 KV 头，所以每 2 个 Q 头共用 1 组 K/V。target 是 8 个 Q 头、4 个 KV 头，比例一样。

好处：KV cache 减半，解码更省内存/带宽；代价：K/V 的表达能力变弱，但 2:1 是很温和的压缩。

### 4.7 FFN、残差、Norm

- **FFN（前馈网络）**：把 256 维升到 768 维，再过激活函数，最后降回 256 维。可以理解成"每个位置自己思考一下"。
- **残差连接**：把输入直接加到输出上，避免深层网络训练时梯度消失。
- **RMSNorm**：把向量归一化，让数值稳定。

### 4.8 输出层

最后一层的向量会被映射回词表大小（1982），得到每个 token 的分数（logits），再经过 softmax 变成概率。

## 5. 第四步：训练

### 5.1 训练循环

每一轮训练做四件事：

1. **前向**：把输入喂给模型，得到对下一个 token 的预测；
2. **算损失**：用交叉熵衡量"预测概率"和"正确答案"差多远；
3. **反向传播**：从损失反推每个参数应该往哪个方向调；
4. **更新参数**：用优化器（AdamW）把参数往"更不容易错"的方向挪一点。

### 5.2 关键超参数

| 参数 | 值 | 含义 |
|---|---:|---|
| epochs | 150 | 把语料完整看 150 遍 |
| batch size | 8 | 每次同时看 8 段 |
| learning rate | 3e-4 | 每次参数更新的步长 |
| warmup steps | 30 | 前 30 步慢慢加大学习率 |
| block size | 256 | 每段长度 |
| seed | 42 | 随机种子，保证可复现 |

### 5.3 实际训练结果

| 指标 | 数值 |
|---|---:|
| 参数量 | 4,162,816 |
| 训练设备 | CPU |
| 最终 train_loss | **2.3624** |
| 训练集 PPL（≈exp(loss)） | **10.62** |
| 训练耗时 | 约 60 秒 |

loss 曲线（抽样）：

| step | loss |
|---:|---:|
| 10 | 7.26 |
| 20 | 6.37 |
| 30 | 5.26 |
| 40 | 4.01 |
| 50 | 3.01 |
| 60 | 2.27 |
| 70 | 1.72 |
| 80 | 1.31 |
| 90 | 1.01 |
| 100 | 0.79 |
| 110 | 0.65 |
| 120 | 0.54 |

注意：曲线里的 `loss` 是**单个 batch 的即时损失**（有波动很正常），而最终 `train_loss=2.3624` 是**整个 epoch 的平均**。两者不是同一个统计口径，不能直接说"从 0.54 涨到 2.36"。

### 5.4 为什么训练 PPL 10.6，评测 PPL 2046

训练集只有 2,667 个字符，模型看了 150 遍，基本把训练文本"背下来了"，所以训练 PPL 很低。

但评测文本是另一段话，模型没背过，就露馅了。这叫**过拟合**：在训练集上表现好，在新文本上表现差。

2046 这个数字是什么概念？词表有 1982 个 token。如果模型完全随机猜，PPL 大约是 1982。**2046 比随机还差一点**，说明这个小模型在评测文本上几乎没学到可泛化的规律。

所以后面看量化对比时，不要看 PPL 的绝对值，而要看**同一个模型、同一段文本下，量化前后差多少**。

## 6. 第五步：评估指标

### 6.1 交叉熵和 PPL

模型对正确 token 给出的概率越高，损失越小。交叉熵是"平均惊讶程度"：

```
loss = -log(模型给正确答案的概率)
```

PPL（困惑度）就是：

```
PPL = exp(平均 loss)
```

可以粗略理解成：**模型平均在多少个候选词之间犹豫。**

- PPL = 10：相当于在 10 个词里犹豫；
- PPL = 100：相当于在 100 个词里犹豫；
- PPL = 1982：基本等于在全部词表里瞎猜。

### 6.2 本项目用到的指标

| 指标 | 含义 | 本项目看什么 |
|---|---|---|
| train_loss | 训练集上的平均损失 | 是否收敛 |
| PPL | 困惑度 | 量化前后质量变化 |
| decode tok/s | 每秒生成多少 token | 解码速度 |
| prefill tok/s | 每秒处理多少 prompt token | 长 prompt 的处理速度 |
| TTFT | 第一个 token 的延迟 | 用户多久看到第一个字 |
| RSS | 进程占用内存 | 部署成本 |
| 接收率 | 投机解码中被 target 接受的 token 比例 | 投机解码是否有效 |

### 6.3 为什么只看 PPL 不够

PPL 只测"预测下一个词"的平均水平，不测：

- 生成内容是否通顺；
- 是否回答了用户的问题；
- 是否安全；
- 首 token 延迟和吞吐。

所以一个完整的部署评估至少要有：质量、延迟、吞吐、内存、成本五个维度。

## 7. 第六步：导出 GGUF

### 7.1 为什么要换格式

训练产物是 HuggingFace 格式：

```
models/tinyllm-hf/
├── config.json
├── model.safetensors
├── tokenizer.json
└── tokenizer_config.json
```

llama.cpp 不直接读这套格式，它读 **GGUF**：一个文件里同时装下模型结构、权重、词表和特殊 token 信息。

### 7.2 导出做了什么

[pipeline/write_gguf.py](../pipeline/write_gguf.py) 做三件事：

1. 读 HF 的 `config.json`，拿到层数、hidden、头数等结构参数；
2. 把 HF 的张量名映射成 llama.cpp 的张量名，例如：
   ```
   model.embed_tokens.weight → token_embd.weight
   model.layers.0.self_attn.q_proj.weight → blk.0.attn_q.weight
   ```
3. 写 GGUF 元数据和权重，矩阵转成 F16，norm 保留 F32。

### 7.3 为什么要自己写导出器

llama.cpp 官方的 `convert_hf_to_gguf.py` 会用"哈希白名单"识别分词器。从零训练的词表不在白名单里，会报：

```
BPE pre-tokenizer was not recognized
```

所以本项目自己写 GGUF，并在文件里声明预分词器是 `gpt-2`，和训练时使用的 GPT-2 正则保持一致。

### 7.4 实际结果

| 指标 | 数值 |
|---|---:|
| F16 GGUF 大小 | 8.45 MB |
| 权重精度 | 16 bit/权重 |
| 架构 | llama |

加载时可能出现一条警告：

```
special_eos_id is not in special_eog_ids
```

这是 llama.cpp 的硬编码 EOG 名单不包含 `<|eos|>` 这个名字，属于**非致命警告**，不影响推理。

## 8. 第七步：量化

### 8.1 为什么需要量化

F16 每个权重占 16 bit。一个 4M 参数的小模型就要 8 MB；如果是 7B 模型，权重就有十几 GB。

更关键的是：**decode 阶段每生成一个 token，都要把所有 weight 从内存读一遍。** 很多时候瓶颈不是算得慢，而是"内存搬得慢"。

量化就是：**用更少的 bit 存权重，读得更少，文件更小。**

类比：把"3.1415926"写成"3.14"，数字短了，但会损失一点精度。

### 8.2 量化的基本公式

最简单的对称量化：

```
q = round(W / scale)
W' = q × scale
```

`W` 是原始权重，`q` 是整数，`scale` 是步长。`q` 只能取有限个值，所以一定有误差。

### 8.3 从 per-tensor 到 per-group

| 粒度 | 一组多少权重共用一个 scale | 优点 | 缺点 |
|---|---:|---|---|
| per-tensor | 整个张量 | 元数据最少 | 离群点会拖垮全部 |
| per-channel | 一个输出通道 | 精度更好 | 元数据变多 |
| per-group | 32 / 128 个 | 精度最好 | 元数据最多 |

LLM 权重里经常有离群点（outlier）。如果整个张量共用一个 scale，一个特别大的数会让其他数都被压得很粗。分小组量化可以把离群点关在小范围内。

### 8.4 Q4_K 的三层结构

Q4_K 是 llama.cpp 的 k-quants 量化方案：

```
一个 super-block = 256 个权重
├── 8 个 sub-block，每个 32 个权重
├── 每个 sub-block 有一个 6-bit scale 和一个 6-bit min
├── 所有 scale 共用一个 FP16 基准 d
└── 所有 min 共用一个 FP16 基准 dmin
```

每个权重的 4-bit 码是 `q`，还原公式：

```
step   = d × sc
offset = dmin × m
W'     = step × q - offset
       = (d × sc) × q - (dmin × m)
```

完整手算例子见 [q4_k_m_quantization.md](./q4_k_m_quantization.md)。

### 8.5 为什么 Q4_K 是 4.5 bit 而不是 4 bit

一个 256 权重的 block 占 144 字节：

| 部分 | 字节 | bit/权重 |
|---|---:|---:|
| 4-bit 权重码 | 128 | 4.0 |
| 8 个 scale + 8 个 min（各 6 bit） | 12 | 0.375 |
| d 和 dmin（FP16） | 4 | 0.125 |
| 合计 | 144 | **4.5** |

### 8.6 Q4_K_M 的 M 是什么

`M` 是 Medium，表示混合精度：

- 大部分张量用 Q4_K；
- `output.weight`、一半的 `attn_v`、一半的 `ffn_down` 用 Q6_K；
- norm 保持 F32。

本项目实际平均是 **4.99 bit/权重**，不是 4.5。

### 8.7 实际量化结果

| 模型 | 方案 | 大小 | 相对 F16 |
|---|---|---:|---:|
| draft | F16 | 8.45 MB | 100% |
| draft | Q4_K_M | **2.71 MB** | **32.1%** |
| draft | Q4_K_S | 2.61 MB | 31% |
| draft | Q8_0 | 4.55 MB | 54% |
| draft | IQ4_XS | 2.48 MB | 29% |
| target | F16 | 39.6 MB | 100% |
| target | Q4_K_M | 12.6 MB | 31.9% |

结论：**量化确实把文件压到了约 1/3。**

### 8.8 量化后一定更快吗

不一定。CPU 上实测：

| 模型 | decode tok/s |
|---|---:|
| F16 | 2173.8 |
| Q4_K_M | 2000.1 |
| IQ4_XS | 1924.5 |

Q4 反而比 F16 慢。原因是反量化本身有开销：每次读 4-bit 码，都要乘 scale、减 offset，才能参与计算。在这个小模型/CPU 上，这点开销盖过了省带宽的收益。

所以"量化 = 更快"是一个常见误解。量化首先保证的是**更小、更省内存**；速度是否提升，要看模型大小、硬件、kernel 实现和并发情况。

### 8.9 量化后精度如何

| 模型 | PPL |
|---|---:|
| F16 | 2046.00 |
| Q4_K_M | 2042.76 |
| IQ4_XS | 2037.78 |

看起来 Q4 还略好一点，但这只是 0.2% 的差异，而且三个值都远高于词表大小 1982，说明模型本身在评测集上几乎等于随机。**这个差异不能用来证明"量化无损"。**

要真正评估量化精度，需要：

- 一个训练得更好的模型；
- 固定、足够长的留出语料；
- 多次测量取中位数；
- 同时看 PPL、top-1 一致率、生成质量。

## 9. 第八步：imatrix 校准

### 9.1 它是什么

imatrix（importance matrix）是"重要性矩阵"：先用校准语料跑一遍模型，统计每个输入通道的激活大小，告诉量化器"哪些通道更重要"。

类比：老师划重点。普通量化对所有章节一视同仁；imatrix 告诉量化器"这几章考试占 80 分，别压缩坏了"。

### 9.2 它怎么影响量化

普通量化最小化：

```
Σ (W - W')²
```

imatrix 加权后最小化：

```
Σ I_j × (W_j - W'_j)²
```

`I_j` 是第 j 个输入通道的重要性。重要通道的误差被放大惩罚，量化器会给它更合适的 scale。

### 9.3 怎么生成和使用

```bash
llama-imatrix -m model-f16.gguf -f calibration.txt -o imatrix.dat -c 512
llama-quantize --imatrix imatrix.dat model-f16.gguf model-q4_k_m.gguf Q4_K_M
```

本项目通过 [quantize_sweep.py](../pipeline/quantize_sweep.py) 的 `--imatrix auto` 自动完成。

### 9.4 本项目的真实状态

配置里写了 `imatrix.enabled: true`，但：

- `export_gguf.py` 的基础 Q4_K_M 路径**不使用** imatrix；
- 现有 `out/quantize_sweep.md` 明确写着 **"重要性矩阵：未使用"**。

所以目前**没有可信的 imatrix A/B 数据**。要验证它，必须固定模型、固定方案，只切换 `--imatrix none` 和 `--imatrix auto`，并用同一份评测语料比较。

### 9.5 校准语料的注意点

- 要和部署场景同分布；
- 不要用评测集（会泄漏）；
- 语料要足够长，llama-imatrix 要求 token 数约为 `2 × ctx`；
- 换模型或换领域后要重新生成。

## 10. 第九步：推理（Prefill 和 Decode）

### 10.1 两个阶段

```
请求到达
  → Prefill：把整个 prompt 一次性读完，填满 KV cache
  → 采样第 1 个 token（到这里是 TTFT）
  → Decode：每次只喂 1 个新 token，读 KV cache，生成下一个
  → ...
```

类比：

- **Prefill**：考试时先把整道题读完、划重点；
- **Decode**：然后一个字一个字写答案。

### 10.2 为什么两个阶段瓶颈不同

- Prefill 一次处理很多 token，同一份权重被复用，算术强度高，通常偏 **compute-bound**；
- Decode 一次只处理 1 个 token，却要读全部权重和 KV cache，算术强度低，通常偏 **memory-bound**。

所以：

- 量化主要省 decode 的带宽；
- 长 prompt 的 TTFT 主要受 prefill 影响；
- 并发高时，TTFT 里还包括排队时间。

### 10.3 KV cache 是什么

Decode 时，历史 token 的 K/V 不需要每步重算，可以缓存起来。缓存大小：

```
2（K 和 V）× 层数 × KV 头数 × head_dim × 每元素字节数
```

本项目 draft 用 GQA（2 个 KV 头）、4 层、head_dim 64、FP16：

```
2 × 4 × 2 × 64 × 2 = 2048 字节/token
512 上下文 ≈ 1 MiB
```

如果用 MHA（4 个 KV 头），就是 2 MiB。GQA 直接省了一半。

### 10.4 实验数据

条件：ctx 512，每次生成 64 token，2 轮取中位数，温度 0，CPU。

| 模型 | TTFT(ms) | prefill tok/s | decode tok/s | RSS(MB) |
|---|---:|---:|---:|---:|
| F16 | 1.9 | 2183.5 | 2173.8 | 32.7 |
| Q4_K_M | 2.2 | 2393.4 | 2000.1 | 29.2 |
| IQ4_XS | 2.1 | 1989.8 | 1924.5 | 27.5 |

### 10.5 怎么读这张表

- TTFT 都在 2ms 左右，因为 prompt 只有十几个字，模型也很小；这个数值**区分度很低**；
- Q4 的 prefill 略快、decode 略慢，差异很小，属于噪声范围；
- 内存确实下降了：32.7 → 29.2 → 27.5 MB；
- 这个实验能证明"链路跑通"，不能证明"Q4 更快"。

### 10.6 KV cache 量化的数据

| 模型 | 原 decode | KV q8_0 decode |
|---|---:|---:|
| F16 | 2173.8 | 1808.4 |
| Q4_K_M | 2000.1 | 2154.4 |
| IQ4_XS | 1924.5 | 1677.7 |

三组结果方向不一致：F16 和 IQ4_XS 变慢，Q4_K_M 变快。这说明在这个小模型/CPU 上，KV 量化的收益被反量化开销和测量噪声掩盖了。**不能得出"KV q8_0 一定更快"的结论。**

## 11. 第十步：投机解码

### 11.1 基本思想

普通 decode：target 大模型每步只生成 1 个 token，慢。

投机解码：

1. draft 小模型先快速猜出 γ 个 token；
2. target 大模型**一次性验证**这 γ 个 token；
3. 猜对的接受，猜错的从 target 的修正分布重新采样；
4. 剩下的草稿丢弃。

类比：小学生先写一份草稿，老师一次性批改。对的留下，错的地方老师改。

### 11.2 为什么不会降低质量

接受-拒绝采样在数学上保证：**最终输出分布和 target 单独解码完全一致**。所以这是"无损加速"，不是拿质量换速度。

### 11.3 前提：共用词表

draft 猜出来的是 token id，target 必须能在同一个 id 上打分。所以两个模型必须共用同一份 tokenizer，词表大小和 id 映射都要一致。

### 11.4 理论加速上限

如果接收率是 α，猜 γ 个 token，每轮期望产出：

```
(1 - α^(γ+1)) / (1 - α)
```

例如 α=0.6、γ=8，期望约 2.47 个 token/轮，理论上限约 2.47×。

### 11.5 实际数据

| 配置 | decode tok/s | TTFT(ms) | 加速比 | 接收率 |
|---|---:|---:|---:|---:|
| target 单跑 | 1028.8 | 2 | — | — |
| target + draft | 1206.4 | 2 | **1.17×** | **—** |

数据来自 `out/spec_decode.md`，条件是 3 个 prompt × 1 轮、温度 0。

### 11.6 为什么只有 1.17×

可能的原因：

- draft 和 target 都是很小的模型，draft 的"猜"本身也要花时间；
- CPU 上验证一次多 token 的收益有限；
- 接收率没有测到，无法判断是猜得不准，还是验证开销太大；
- 1 轮样本太少，噪声大。

所以这个实验能说明"投机解码链路跑通、有加速"，但不能说明"已经调到最优"。

## 12. 第十一步：LoRA SFT

### 12.1 预训练 vs 指令微调

- **预训练**：让模型学会"预测下一个词"，但不会回答问题；
- **SFT（监督微调）**：用"指令 → 回答"的样本，教模型按人类期望的格式回答。

### 12.2 LoRA 是什么

全量微调要更新所有参数，代价大。LoRA 只训练一小对低秩矩阵，把它加到原来的权重上：

```
W_new = W_old + B × A
```

原来的 `W_old` 不动，只训练 `A` 和 `B`。类比：在原书上贴便签，不改原书。

### 12.3 实际数据

| 指标 | 数值 |
|---|---:|
| 训练样本 | 17 条 |
| 训练轮数 | 3 |
| 可训练参数 | 155,648（3.60%） |
| 最终 loss | 7.3925 |
| 设备 | CPU |

### 12.4 怎么解读

- 链路跑通了：LoRA 训练 → 合并 → 保存 HF 模型；
- 但 17 条样本太少，3 轮也很难学会稳定的指令遵循；
- loss 7.39 不能和预训练的 2.36 直接比，因为数据、目标、token 数都不一样；
- 现有报告没有在同一个基准上比较 base 和 SFT 的质量。

所以"SFT 有用"目前只能算"流程可用"，不能算"效果已验证"。

## 15. 为什么这些结论不能乱下

### 15.1 PPL 的绝对值不可信

PPL 2046 > 词表 1982，说明模型在评测集上比随机还差。三个量化方案的 PPL 差 0.2%，完全是噪声。

### 15.2 TTFT 只是 prefill 的代理

代码取的是 llama-server 的 `prompt_ms`，不包含网络、排队和第一个 token 的采样。prompt 只有十几个字，所以 TTFT 只有 2ms，没有区分度。

### 15.3 imatrix 没有真正参与

配置里写了 enabled，但基础导出路径不用它，sweep 报告也写着"未使用"。

### 15.4 GQA 没有对照

两个模型都用 GQA，没有 MHA 版本，所以不能说"GQA 带来了多少提升"。

### 15.5 部分产物可能不是同一批

`out/benchmark.md` 生成于 10-05，而最新一次训练/导出是 10-07。跨批次比较可能把"重新训练"的差异算到量化头上。严谨实验必须用同一次训练的 F16 生成所有量化版本。

### 15.6 投机解码缺少接收率

没有接收率，就无法判断 1.17× 是"猜得准"还是"验证开销小"，也无法调参。

---

## 16. 如果要得到更可信的结论，怎么做

### 16.1 控制变量

每次只改一个东西：

1. 固定 F16 模型，只改权重精度；
2. 固定 Q4_K_M，只改 imatrix 开关；
3. 固定模型，只改 KV cache 类型；
4. 固定 target 权重，只改是否加 draft；
5. 固定精度，只改是否 SFT。

### 16.2 用同一批产物

先训练一次，导出 F16，然后**所有量化版本都从这份 F16 生成**，不要混用旧文件。

### 16.3 用固定、够长的评测语料

- 至少几千 token；
- 不要和训练集重叠；
- 每次实验都用同一份；
- 记录语料哈希。

### 16.4 多次测量

- 至少 3–5 轮；
- 报告 p50 / p99，而不只是平均值；
- 记录机器型号、线程数、llama.cpp build 号。

### 16.5 同时报告质量、延迟、吞吐、内存

一个方案只有在"质量可接受"的前提下，速度和内存的比较才有意义。

| 术语 | 一句话解释 |
|---|---|
| token | 文本被切出的小块，模型处理的基本单位 |

## 19. 最后一段话

如果你是第一次接触深度学习，最重要的不是记住所有公式，而是记住这条因果链：

```
文字 → token → 向量 → 注意力 → 预测下一个词 → 算损失 → 调参数
     → 模型文件 → 量化压缩 → 推理服务 → 测量质量/延迟/成本
```

这个项目里的每一个脚本，都是这条链上的一环。先能用自己的话讲清楚每一环"为什么存在"，再去抠细节，会比一上来背公式有效得多。
